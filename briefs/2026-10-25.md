## Regressions and risks

**Invariant 1 — mentor session is the dearest thing on the site: HOLDS.**
`MENTOR_CENTS` 2900 > dearest product 2000 (bundle). Enforced at import time by the
`throw` in `src/lib/products.ts`, so a violation fails the Vercel build rather than
shipping.

**Invariant 2 — bundle costs more than either product it contains: HOLDS, by $2.**
Bundle 2000 > careers 1800 > cv 500. **Still not enforced in code.** The file
documents rule 2 as loudly as rule 1 but only rule 1 has a runtime guard. Any future
rise in `CAREERS_CENTS` above 2000, or drop in `BUNDLE_CENTS` below 1800, silently
makes the $18 careers report strictly dominated and unsellable with no build error.
The missing guard is four lines mirroring the one above it. Unchanged from last week.

**Paywall slicing rule: HOLDS in all three routes.** Each prompt asks for the full
ranked answer and the server slices the free tier off the END:

| Route | Prompt asks for | Free tier |
|---|---|---|
| `src/app/api/essay/route.ts:107,149` | "Give the FULL review — every fix worth making" | `allTips.slice(-3)` — weakest 3 |
| `src/app/api/cv/route.ts:110,149` | "Give the FULL review — every fix worth making" | `allTips.slice(-2)` — weakest 2 |
| `src/app/api/careers/route.ts:175,222` | "Produce a full career report", ordered best-fit first | `careers.slice(-1)` — weakest 1 |

All three instruct the model never to mention free/paid/unlocking, and all three gate
on `PAYWALLS_ENABLED && entitled`. No regression.

**`src/lib/leads.ts` key parsing: still correct.** `leads.ts` scans `fledgy:tools:*`
and `fledgy:usage:*`, takes the segment after the LAST colon, and discards anything
without an `@` — which reads both the old `fledgy:usage:<email>` and the current
`fledgy:usage:<tool>:<email>`. Grepping every `fledgy:` literal in `src/` finds twelve
key families (`ent`, `stripe:session`, `report`, `unsub-token`, `unsub`, `autoreply`,
`autoreply:tool`, `backfill:whatsnew`, `leads`, `lead`, `leadseen`, `inquiries`,
`usage`, `bonus`, `referredby`, `referralpaid`); both families the dashboard actually
scans still end in the email, and no key under those two prefixes can produce a
non-email tail. **No key gained or lost a segment this week.** No garbage rows.

One structural gap, not a break, carried from last week: the scan covers only those
two families, so an email known **only** from `fledgy:ent:<email>` (a purchase) would
not appear. In practice a buyer is always a prior tool user, so nothing is hidden
today — but the first real customer is the case that tests it.
