## Regressions and risks

**Both pricing invariants hold.**

- **Rule 1 — mentor session is the dearest thing on the site: HOLDS.** `MENTOR_CENTS` 2900 >
  dearest product 2000 (`BUNDLE_CENTS`). Still enforced at import time by the `throw` in
  `products.ts`, so a bad price fails the Vercel build rather than shipping.
- **Rule 2 — bundle costs more than either product it contains: HOLDS.** `BUNDLE_CENTS` 2000 >
  `CAREERS_CENTS` 1800 and > `CV_CENTS` 500. The derived saving line reads `$3`, which is
  arithmetically correct (500 + 1800 − 2000).
  *Worth noting, not a break:* after `5ac5d4c` dropped the CV to $5, the bundle sits only **$2
  above the standalone careers report**. Rule 2 is intact but the margin is now thin enough that
  any further cut to `CAREERS_CENTS`, or any rise in `BUNDLE_CENTS`'s neighbours, needs a second
  look. Unlike Rule 1, Rule 2 is **documented but not enforced by a runtime check** — there is no
  `throw` guarding it.

**Paywall slicing rule holds in all three routes.** Each prompt asks the model for the full ranked
answer and each route slices server-side from the **end** of that array:

| Route | Prompt asks for | Server slice |
|---|---|---|
| `src/app/api/essay/route.ts:107,149` | "Give the FULL review — every fix worth making" | `allTips.slice(-3)` |
| `src/app/api/cv/route.ts:110,149` | "Give the FULL review — every fix worth making" | `allTips.slice(-2)` |
| `src/app/api/careers/route.ts:190,222` | "ORDERED BEST-FIT FIRST … This ordering is load-bearing" | `careers.slice(-1)` |

No route asks the model for less. The essay route still carries the comment recording the old
`slice(0, 1)` bug, so the regression it describes has not come back.

**`leads.ts` key parsing holds.** Grepping `fledgy:` across `src/` turns up these families:
`usage:<tool>:<email>`, `usage:<email>` (legacy), `tools:<email>`, `lead:<email>`, `leads`,
`leadseen:<email>`, `ent:<email>`, `report:<email>`, `autoreply:<email>`,
`autoreply:tool:<tool>:<email>`, `bonus:<email>`, `backfill:whatsnew:<email>`,
`referredby:<email>`, `referralpaid:<email>`, `unsub:<email>`, `unsub-token:<email>`,
`stripe:session:<id>`, `inquiries`. `getAllLeads` scans only `fledgy:tools:*` and `fledgy:usage:*`
and takes the segment after the **last** colon, which reads both usage shapes correctly. The
`email.includes("@")` guard means an unrecognised shape is skipped rather than rendered as a
garbage row — including `stripe:session:<id>`, which has no `@`. **No breakage.**
*Minor completeness gap, not a bug:* an email known only from `fledgy:ent:` or `fledgy:report:`
(a buyer whose tool/usage keys expired) would not appear on the dashboard.
